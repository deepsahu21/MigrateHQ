TASK
Fix schema drift and hardcoded tenant in the data write path. Two issues:
(1) backend/schema.sql missing three columns that application code already reads/writes.
(2) write_to_supabase() in bigquery_loader.py hardcodes tenant='olist', silently failing for any other tenant.

       ALTER TABLE mapping_results ADD COLUMN IF NOT EXISTS target_samples JSONB;

WHAT WAS BUILT

Issue 1 — Schema sync:
backend/schema.sql now matches what the application actually writes. The three columns
(source_samples, target_samples, explanation) are defined in the CREATE TABLE block,
so fresh Supabase deployments get them automatically. The ALTER TABLE ADD COLUMN IF NOT EXISTS
statements at the bottom make the file safe to run against the existing live Supabase DB —
they are no-ops if the columns already exist, and add them if they don't.

Data types chosen based on what the code actually writes:
- source_samples / target_samples: Python lists of strings produced by .tolist() in
  orchestrator.py. supabase-py serializes these as JSON arrays, so JSONB is correct.
- explanation: Plain string from Gemini response.text.strip(), so TEXT is correct.

Issue 2 — Tenant parameter:
write_to_supabase() now accepts a tenant_name parameter (default "olist", preserving
backward compatibility). run_mapping_pipeline() also accepts tenant_name and threads it
through to write_to_supabase(). Callers that do not pass tenant_name continue to behave
exactly as before. Callers that pass a different tenant name will now correctly look up
that tenant in the tenants table instead of silently skipping on mismatch.

ASSUMPTIONS MADE

1. JSONB over TEXT[] for samples: source_samples and target_samples are Python lists,
   which supabase-py sends as JSON. JSONB is idiomatic in Supabase for structured data
   and more queryable than TEXT[]. TEXT[] would also work but would require the client
   to send a Postgres array literal.

2. Default tenant_name="olist": The existing callers (tests, __main__ blocks) don't pass
   a tenant. Defaulting to "olist" keeps them working without changes. If the intent was
   to force callers to be explicit, the default should be removed — but that would break
   existing call sites.

3. ALTER TABLE statements placed after the INSERT block: The existing schema.sql runs
   CREATE TABLE IF NOT EXISTS first, then seeds tenants. The ALTER TABLE statements are
   appended at the end so the file remains top-down executable in a single pass on both
   fresh and existing DBs.

4. The live Supabase DB already has these columns (write_to_supabase has been writing
   to them in production). The ALTER TABLE statements are defensive — they apply the
   schema correctly if the DB was provisioned from schema.sql before the columns existed.

---

KNOWN LIMITATIONS / NOT DONE

- The tenant fix only affects the Supabase write mirror. push_mapping_to_bigquery() has
  no tenant concept — BigQuery results are not partitioned by tenant, only by source_dataset.
- write_to_supabase() is still hardcoded to look up the tenant by exact name match. If
  the tenants table has no row matching tenant_name, the write silently skips. There is
  no fallback or auto-creation of tenants.
- The __main__ block in orchestrator_pipeline.py uses dataset_name="olist_stage1" and
  does not pass tenant_name, so it still defaults to "olist". This is correct for the
  current pilot but not general.
- No migration tooling (Alembic, supabase migrations) exists in this repo. schema.sql
  with ALTER TABLE is a manual-run file, not an automated migration.
